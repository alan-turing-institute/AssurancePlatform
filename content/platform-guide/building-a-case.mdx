This page is a reference for the case editor, not a walkthrough.
If you want to build something step by step first, see [Module 2 of the TEA Trainee curriculum](/docs/curriculum/tea-trainee/02-brewing-your-own-tea), which uses the same controls described here on a worked example.

## Create a case

From the dashboard, choose **New Case** (or the **Create new case** card if you already have cases) and fill in **Name** and **Description** in the **Create New Assurance Case** dialog, then choose **Submit**.
This creates a blank working case with a single top-level goal, named `G1` and holding a placeholder description for you to replace.
There is no starter-template choice in this dialog; a separate **Import File** option on the dashboard creates a case from an existing JSON export instead.

## Element types

An assurance case is built from ten element types, each with a fixed one- or two-letter prefix used in its generated name:

| Element | Prefix | Example name |
| --- | --- | --- |
| Goal | `G` | `G1` |
| Strategy | `S` | `S1` |
| Property Claim | `P` | `P1` |
| Evidence | `E` | `E1` |
| Context | `C` | `C1` |
| Justification | `J` | `J1` |
| Assumption | `A` | `A1` |
| Module | `M` | `M1` |
| Away Goal | `AG` | `AG1` |
| Contract | `Ct` | `Ct1` |

Goals, strategies, property claims and evidence make up the argument tree you build with the **+** control described below.
Context, justification and assumption are added directly on the element they qualify, through its edit dialog rather than the `+` menu.

## Add and edit elements

Each node on the canvas carries a **+** control, labelled **Add child element**.
It opens a popover offering the child types valid for that node. A goal offers **Add Strategy** and **Add Property Claim**; a strategy offers **Add Property Claim**; a property claim offers **Add Strategy**, **Add Property Claim** and **Add Evidence**. **Add Defeater**, **Add Away Goal** and **Add Module** are offered alongside those on all three node types.
Evidence nodes have no `+` control, since nothing can be added beneath them.

The pencil icon on a node, labelled **Edit element** (or **View details** if you only have view or comment access), opens that element's edit dialog.
The dialog's fields depend on the element type — a description for every type, plus **Context** entries and an **Assertion status** selector on goals and property claims, and an optional assumption or justification field where relevant.
Saving calls the dialog's submit button, labelled **Update** followed by the element type — **Update Goal**, **Update Strategy**, **Update Property**, **Update Evidence** and so on.

## Defined terms

A context entry can be given a name, so that the description of the element it sits on, and of every element below it, can refer to it.
This lets you define a word once, for example `window` as "the moving 5-minute interval over which separation is measured", and use it in the claims beneath.

### Name a context entry

In the edit dialog of a goal, strategy or property claim, each context entry has a tag button, labelled **Name context entry 1**, **Name context entry 2** and so on.
Choose it, then type the name.
The entry's own text becomes the name's meaning.
You can also give the entry a value, such as `5 minutes`, in the box beneath its text.
The value is optional.

A name is 1 to 40 characters.
It starts with a letter and uses letters, digits, spaces, hyphens and underscores.
A value is at most 500 characters.
One element cannot have two names that differ only in capital letters, such as `Window` and `window`.

**Remove name** turns the entry back into ordinary text.
If the entry has a value, the dialog warns that the value goes with the name, and asks you to confirm.
Text that referred to the name then shows it as not found.

### Use a name in a description

In the description of a goal, strategy or property claim, type `{`.
A list opens beside the cursor with the names the element can use.
Each name is labelled with the element it is defined on, and the nearest definition comes first.
Keep typing to narrow the list.
Press the arrow keys and **Enter**, or click a name, to insert it as a highlighted word.
Press **Escape** to close the list; the `{` stays in the text, and the dialog and anything you have typed stay as they are.
Typing `}` closes the list too, so braces you mean as plain text are left alone.

The description box takes paragraphs and references.
It has no other formatting.
Pressing **Enter** starts a new paragraph.

A name reaches the element that defines it and every element below it on the same branch.
It does not reach an element on another branch.
If two names in reach are the same, the list shows both, with the nearer one first.

Under the description, **Terms you can use here** lists every name in reach with its meaning, its value and the element it is defined on.
Use it to read a meaning without a mouse.

### See a name on the diagram

On a card, a reference appears as a highlighted word that shows the entry's current name.
Rename the entry and every reference follows.
Hover over the word on an expanded card to see its meaning, its value and the element that defines it.
On a collapsed card the word is highlighted without its own tooltip, and hovering a description that is cut short shows its full text, with each reference written `{name}`.
An expanded card's **Context** section lists each named entry as the name, its meaning and its value in brackets.

If the definition is no longer in reach, the word stays but is underlined with a dashed line, and its tooltip says that no definition was found above the element.
This happens when the entry is deleted or has its name removed, or when the element moves to another branch.
Screen readers announce the word followed by "(definition not found)".

Evidence, away goal and module cards do not resolve references.
Evidence can sit under several claims, so the names it could use are not fixed, and any reference in the text of one of these cards shows as `{name}` without a highlight.

### Where else you see a reference

Search, the move and attach lists, document exports, the [Case Assistant](/docs/platform-guide/case-assistant) and the rules check show a reference as `{name}`.
Raw JSON exports keep the stored form, `{name#id}`, where the id is what ties the reference to its entry.

## Assertion status

Goals, strategies and property claims carry an assertion status, set from the edit dialog.
There are five values an author can choose from:

- **Asserted** — the author's stated position. This is the default.
- **Needs support** — flagged by the author as requiring further evidence.
- **Assumed** — taken as given by the author rather than argued for.
- **Axiomatic** — treated by the author as self-evidently true in this case.
- **Defeated** — marked by the author as refuted or withdrawn.

<Callout type="info">
A sixth status, **As cited**, can appear on an element, but you cannot set it directly. It is not computed automatically in this build; it arrives only when a case is imported with that status.
</Callout>

Assertion status records the author's own position; it is not an automated verdict on whether the evidence is actually sufficient.

### The Unsupported marker

A goal, strategy or property claim with nothing beneath it carries a small badge reading **Unsupported**, drawn with a dashed outline.
The marker shows where an argument stops.
Hover over it for a reminder of how to clear it.

An element counts as supported when at least one of these sits directly beneath it:

- a strategy or a property claim;
- a piece of evidence;
- an away goal or a module, even when its link to the other case or module is broken.

A defeater does not count, because it challenges the element it is attached to rather than supporting it.
A claim whose only child is a defeater is still marked.
Collapsing a branch hides its children without removing them, so a collapsed element is never marked for that reason.

The marker sits on the element with nothing beneath it, not on the elements above it.
Add a strategy under an unsupported goal and the marker moves to the strategy.
Add a claim under that strategy and it moves to the claim.
Add evidence under the claim and it clears.

The marker does not appear on evidence, away goals, modules or defeaters, which end a branch by design.
It also does not appear once you have set a status that explains why nothing is beneath the element.
**Needs support** shows its own badge instead, and **Assumed**, **Axiomatic**, **Defeated** and **As cited** show no marker.
An element with the default **Asserted** status can carry the marker.

The marker is different from the **Needs support** status.
**Needs support** is your own declaration that an element still needs work, and it is saved with the case.
The marker is worked out from the diagram each time it is drawn.
It is never saved, so it does not appear in a JSON export or on import, and it never changes a status you have set.
It is also left out of exported images and the dashboard thumbnail, and out of the example diagrams in the documentation.

Each person chooses whether to see the marker.
Use **Show unsupported markers** in the **Settings** menu on the case toolbar, or in the **Case diagram** section of the account **Settings** page.
The choice is saved to your account, so it applies in every browser you sign in from, and it starts on.
Other people viewing the same case see the marker by their own setting.

## Element names and the prefix rule

The editor generates each element's name automatically — you do not type one in the add or edit dialogs.
If you import a case from JSON, any named element must follow the same pattern its type uses: a prefix followed by a number, optionally extended with dotted sub-numbers (for example `P1`, `P1.1`, `G2`).
An import that breaks this pattern is rejected.

If names in your working case get out of order — after a lot of adding, deleting and restructuring — the toolbar's **Reset Identifiers** control renumbers every element using the same hierarchical naming the editor generates automatically. It requires edit access on the case.

## Undo, redo and the toolbar

The toolbar's history controls are **Undo** (`Cmd+Z`) and **Redo** (`Cmd+Shift+Z`); both operate on your recent add, edit and delete actions within the current session.

The **Export** control opens the **Export Case** dialog, which offers four independent ways to take a copy of your case:

- **Export Raw JSON** — the case data itself, suitable for import elsewhere.
- **Export as Image** — a rendered picture of the diagram.
- **Export Report** — a document summarising the case, including a full-report option.
- **Backup to Google Drive** — saves a JSON copy to your Google Drive, if your account is connected.

None of these dialogs has a separate whole-case "Save" button.
Every add and edit dialog persists its own change the moment you submit it; export and backup are separate actions for taking a copy, not for saving your work.

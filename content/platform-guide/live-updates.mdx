---
title: "Live case updates"
description: "See how a shared case responds when another collaborator changes it."
---

When two people have the same case open, the editor listens for changes to that case. A second person's edit can update your view without a manual page reload. This helps collaborators see a current argument while they discuss it, but it is not a shared cursor or a lock that prevents simultaneous editing.

## What you see

Open a case you can view at `/case/<caseId>`. The browser connects to the case's event stream. If another person changes case details, adds or edits an element, moves it, changes a comment, or changes a permission, the case container requests fresh case data. Attachment and detachment events also refresh orphaned elements. For supported case, element and comment events, the editor can show a short notice naming the person and action, such as a new element or a comment. The notice uses event data when available and falls back to a generic name when it is not.

You do not need to select a refresh control to receive those events while the connection is active. Your own actions are not announced back to you as another person's toast. If you are comparing a long description or preparing a review, pause and read the refreshed state before editing the same element. Live updates keep the view current, but they do not reconcile two competing edits at the sentence level.

## How it works and where it stops

The editor uses a server-sent event connection to `/api/cases/<id>/events`. The route checks the browser session and case `VIEW` access before opening a stream. Route handlers and services emit typed events after case, element, comment and permission changes. The client listens for the types it knows, waits briefly to combine nearby events, then refetches the case. The server sends each stream a heartbeat every 25 to 30 seconds, a slightly different period for each stream, which keeps the connection active.
Each heartbeat also checks again that you can still view the case, and ends your stream if you cannot, for example after your access is removed or the case is trashed or deleted.
Removing your last access also starts that check at once, so you do not wait for a heartbeat.
This covers a direct share being removed, a team being unshared from the case, you being removed from a team or leaving it, a team being deleted, and the case being moved to Trash.
Any other change that removes access, such as deleting an account, is picked up at the next heartbeat.
Just before the server ends your stream it sends a `stream:closed` event, and the editor replaces the case with an **Access removed** message and a link back to the dashboard.
Each heartbeat check also looks at whether your session is still the current one.
Changing or resetting your password ends your sessions, so within 30 seconds the server closes every stream you have open, with a `stream:closed` event whose reason is `signed-out`, and the editor takes you to the sign-in page.
If your browser misses either event, for example because the server restarted, the editor asks the events route once for its status: a 404 shows the **Access removed** message, and a 401 takes you to the sign-in page.
The editor does not try to reconnect after any of these.
The browser's event source can reconnect after a temporary interruption, but the stream is a notification channel rather than a durable record of every historical edit.

The connection manager holds subscribers in server memory, grouped by case. It has no shared broker across independent server processes, so deployment topology matters for delivery between people connected to different processes. If a view appears stale, reopen the case or refresh before relying on it for a review decision. Comment events and health plugin state changes are distinct event types; the client has specific handling for each surface rather than treating every event as a full document replacement.
The health plugin's evidence nodes follow the same events: the canvas reads again which evidence nodes show a claim's result after every event that makes it reload the case, and after every health status change, so a node's colour and badge change when a result arrives and when the node is moved, trashed or restored.
A result that expires while the page is open fades its node and line on this device's clock, without waiting for an event.

## Limits and code location

Live events do not expose a collaborator's pointer, indicate that an element is locked, or replace explicit saving and review. `app/api/cases/[id]/events/route.ts` serves the stream, `lib/services/sse-connection-manager.ts` broadcasts events, `hooks/use-case-events.ts` listens in the browser, and `components/cases/case-container.tsx` refreshes the displayed case.
